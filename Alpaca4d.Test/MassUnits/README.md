# Mass units

Guards the one rule that every mass in the model has to obey: **the user types kg, the
solver is given tonnes.**

OpenSees has no unit system. `mass` writes its arguments straight onto the diagonal of the
node's mass matrix, an `nDMaterial`'s `rho` is read back by every solid and shell as mass per
unit volume, and a beam's `-mass` is mass per unit length — and `DOF_Group::addMtoTang` and
`FE_Element::addMtoTang` then add all of them into the same matrix at a factor of one. With
kN, m and s the consistent mass unit is kN·s²/m, the tonne, so everything crossing into a
deck goes through `Alpaca4d.ModelMass`.

This existed because the conversion used to be written out by hand at each call site and
three of the four got it wrong:

| Path | Was | Effect |
| --- | --- | --- |
| beam `-mass` | `A·ρ/1000` | correct |
| point `mass` | `kg · 9.81/1000` | 9.81× too heavy — periods √9.81 ≈ 3.13× too long |
| shell / brick / tet, via `nDMaterial rho` | `kg/m³` raw | 1000× too heavy — frequencies √1000 ≈ 31.6× too low |
| `node -mass` | one raw scalar on all 6 DOFs | dead, and unusable — see below |

## Only one route to concentrated mass

`Node` used to carry a `double Mass` written as `node $id $x $y $z -mass m m m m m m`: one
number standing in for both a mass and a mass moment of inertia, with no unit conversion. It
was never assigned and could not be — the nodes that reach a deck are built inside
`Model.CreateNodes` from the model's own points.

It could not have worked in any case. Both `node -mass` and `mass` land on
`Node::setMass`, which **assigns rather than accumulates**, and Alpaca4d writes every node
before any mass — so a `MassLoad` at the same node would have overwritten it silently:

    node 2 0 0 3 -mass 5 5 5 0 0 0
    mass 2 1 1 1 0 0 0             ->  the node ends up with m = 1, not 6

So the node line no longer carries mass at all, and `MassLoad` is the single route.
Omitting `-mass` is equivalent to writing zeros: `Node::getMass` returns a zeroed matrix
when none was set.

## What it checks

**Part 1 — `MassUnits.cs`** asserts the exact Tcl `Alpaca.Core` emits: `nDMaterial`
isotropic and orthotropic `rho`, a point `mass` line including the rotational terms, and the
beam mass density. It also checks that masses on one node are added up into one `mass` line:
`mass` sets a node's mass too, so of two Mass Points on one node only the last used to count.
It writes the lines it produced to `alpaca_lines.txt`.

**Part 2 — `cross_element.py`** builds the *same* cantilever — L = 6 m, 0.4 × 0.1 m, steel,
ν = 0 so a strip behaves exactly as a beam — three ways, and solves each with OpenSees:

* `forceBeamColumn` × 24
* `ASDShellQ4` 48 × 4
* `SSPbrick` 48 × 4 × 4

The material and section lines come **verbatim from part 1**, so the physics is driven by
Alpaca4d's real serialisation; only node and element topology, which carries no units, is
generated by the script. Every model must land on the closed-form first mode

    f1 = (1.875104)^2 / 2pi . sqrt(EI / (m L^4)) = 2.3209 Hz

and on each other. They currently agree to better than 0.1 %.

It then checks concentrated mass on its own, as an exact SDOF: a massless cantilever with
1000 kg at the tip, against `f1 = sqrt(3EI/L^3 / m)/2pi`.

The script finishes by re-running the shell and brick with `rho` written raw, to show the
31.6× error the fix removed.

## Running it

    ./run.sh

Not wired into `Alpaca4d.sln` — it drives a compiled `Alpaca4d.Core.dll` and an external
OpenSees, so it is a benchmark you run, not part of the build.
